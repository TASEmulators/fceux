## Context

现有 Win32 汉化已经提供 `en-US`/`zh-CN` 资源、语言选择、宽字符加载、英文回退和少量按英文原文映射的动态字符串包装器。静态菜单和对话框可随语言切换，但 `src/drivers/win` 的历史代码仍通过 `MessageBox`、`SetWindowText`、`SetDlgItemText`、文件选择器、状态栏、工具提示及动态菜单等路径直接产生英文文案；其中既有固定 UI 文本，也有路径、设备名、地址和调试输出等不应翻译的数据。

这项工作横跨主窗口、输入/音视频配置、调试工具、Movie/Lua 和 TAS Editor。实现必须兼容项目现有的非 `UNICODE` 编译设置和较老的 Win32 代码结构，并以 Visual Studio 2022 `v143` 的 `Release|Win32` 构建为验收门槛。

## Goals / Non-Goals

**Goals:**

- 找出并审计 Win32 C/C++ 源码中所有可能显示给用户的固定字符串。
- 将应翻译的固定文案改为稳定资源 ID，通过现有语言选择、宽字符 API 和英文回退机制显示。
- 以大众通行理解为准执行保守术语分类，保证专有名词、格式名、工具名、缩写和独有 TAS/NES 术语不被生硬翻译。
- 保持格式参数、快捷键信息、运行数据和已有命令行为不变。
- 用可重复的静态检查阻止新的未登记英文 UI 字面量进入 Win32 前端。
- 保持 `v143` 的 x86 Win32 构建成功，并完成中英文动态界面冒烟验证。

**Non-Goals:**

- 不重新翻译 `res.rc` 中已完成的菜单、对话框和静态控件正文；允许为源码动态文案新增双语 `STRINGTABLE` 条目。
- 不汉化日志文件、调试数据、反汇编、脚本输出、命令行输出、配置键或内部协议字符串。
- 不以“尽量减少英文”为目标，不为缺少稳定大众译法的专有概念创造中文名称或缩写。
- 不修改 Qt/SDL 前端、模拟核心、ROM/存档/Movie 文件格式或文件 I/O 编码语义。
- 不将整个 Win32 工程切换为 `UNICODE`，也不引入外部语言包或第三方国际化库。

## Decisions

### 1. 以“候选扫描 + 人工分类清单”确定覆盖面

校验脚本扫描 `src/drivers/win` 的 C/C++ 文件，覆盖消息框、窗口/控件标题、状态栏、工具提示、动态菜单、文件对话框以及其他已识别的可见文本入口。每个候选必须在审计清单中标记为 `translate`、`preserve` 或 `exclude`，并记录文件位置、调用场景和保留/排除理由。

仅依赖正则无法理解所有历史 C++ 数据流，但只做人工搜索又无法防止回归；两者结合能够在不引入 Clang 等构建依赖的前提下提供稳定、可审查的基线。扫描规则允许明确登记的误报，但不允许未登记候选静默通过。

### 2. 术语先通过保守判定门槛，再进入翻译

审计清单为涉及术语的候选记录 `termKind`、`decision` 和 `reason`。判定顺序如下：

1. 产品、项目、人物或组织名称，官方工具/模块名称，文件格式、协议、扩展名、品牌词、缩写，以及只在 TAS/NES 领域使用的独有概念，归为专有名词并默认 `preserve`，保持原拼写和大小写。
2. 普通菜单动作、状态、确认/错误提示等通用界面词可归为 `translate`。
3. 领域词只有在简体中文模拟器/TAS 用户中存在单一、稳定且易理解的通行译法时才归为 `translate`；清单必须记录采用依据。
4. 无法确认类别、存在多种竞争译法或直译可能改变技术含义时，一律 `preserve`。不得为了减少界面英文而逐字硬译或自创译名。

复合文案按 token 处理，例如可翻译 `Open ROM` 中的普通动作 `Open`，但 `ROM` 必须保留。术语依据优先采用项目/格式的官方拼写和既有标识，再参考当前术语表与简体中文模拟器/TAS 社区的长期通行用法；这些依据发生冲突时选择保留英文。这样会留下少量英文，但比产生误导性译名更稳妥，也便于以后用明确证据调整单项结论。

### 3. 新迁移文案采用资源 ID，而不是扩大英文原文查表

每个固定 UI 模板分配 `IDS_LOC_*` ID，在英文和简体中文 `STRINGTABLE` 中成对定义。调用点显式加载 ID，并传给 `MessageBoxW`、`SetWindowTextW`、`SetDlgItemTextW` 或对应宽字符 API。现有按英文原文匹配的兼容包装器可继续服务已迁移代码，但新工作不依赖英文字符串作为主键。

资源 ID 在重构和措辞调整后仍稳定，也能直接验证双语覆盖；英文原文查表虽然改动较小，但容易因标点、拼接或重复短语造成漏译和语境错误。

### 4. 固定模板与运行数据分离

带变量的文案拆成资源模板和运行参数。英文与中文模板必须保持相同数量、顺序和类型的格式参数；设备名、文件名、路径、ROM 名称、数值、地址、寄存器和脚本/调试输出不翻译。宽字符格式化在 UI 边界完成，原有数据对象和文件操作参数不因本地化改变。

对频繁更新的纯运行数据控件不做无意义的资源化；只有其中固定的标签、前缀、后缀和提示需要本地化。

### 5. 文件对话框按调用点迁移到宽字符结构

文件对话框标题和筛选器使用资源化的宽字符文本，并由 `OPENFILENAMEW`/对应 `*W` API 显示。筛选器保留双 NUL 结构、扩展名模式及顺序；选择结果在既有文件处理边界按项目现有约定传递，迁移不得顺带改变文件 I/O 行为。

不全局定义 `UNICODE`，因为这会改变大量未审计 Win32 API、结构体和第三方接口的类型，扩大回归范围。

### 6. 分模块迁移并以 `v143` 持续验证

迁移按主窗口/文件流程、配置模块、调试与内存工具、Movie/Lua/TAS Editor 分批完成。每批更新资源、调用点和审计清单后运行本地化检查；关键批次及最终状态使用 VS2022 MSBuild、`Configuration=Release`、`Platform=Win32`、`PlatformToolset=v143` 构建。

## Risks / Trade-offs

- [宏包装器可能掩盖未显式迁移的字面量] -> 校验以调用点和审计清单为准，新文案要求显式资源 ID，并逐步减少对英文原文映射的依赖。
- [静态扫描出现误报或漏掉间接数据流] -> 覆盖多类 UI sink，保留带理由的 allowlist，并通过中文界面逐窗冒烟补足静态检查盲区。
- [“大众通行译法”可能存在主观判断] -> 先排除所有专有名词类别；其余领域词必须记录稳定用法依据，无法给出单一结论时保留英文，并在最终人工复核中逐项确认。
- [复合文案翻译时误改专有名词] -> 清单记录必须保留的英文 token，校验脚本比较其拼写和大小写，人工验收再检查最终显示文本。
- [中文模板的格式参数不匹配导致运行错误] -> 自动比较双语资源中的格式说明符，并为代表性格式化文案执行定向检查。
- [ANSI/Unicode 边界破坏路径或用户数据] -> 仅在显示边界转为宽字符，不改变底层数据所有权和文件 API 语义，并用 Unicode 路径做回归验证。
- [新增中文文本在紧凑工具窗口中截断] -> 优先使用术语表短译，逐窗检查 100% 与项目支持的高 DPI，必要时只做最小布局调整。
- [与既有 Win32 汉化变更重复记账] -> 本变更清单只收录源码动态文案，并在实现完成后同步勾选原变更对应的动态文案任务，避免两套实现。

## Migration Plan

1. 固化源码候选扫描结果，先完成术语类别、处理结论和依据审查，不改变运行行为。
2. 冻结专有名词保留 token；只有通过术语门槛的通用文案才能进入翻译清单。
3. 扩展资源 ID、双语字符串表和显式宽字符加载/格式化入口。
4. 按模块迁移调用点，每批同步审计清单和自动化检查。
5. 运行本地化检查与 `v143 Release|Win32` 构建，再完成中英文逐窗冒烟和术语复核。
6. 如需回滚，可按模块恢复调用点并移除对应未使用资源 ID；英文原行为和静态资源不受其他批次影响。

## Open Questions

无。具体字符串的 `translate`、`preserve` 或 `exclude` 结论在实现阶段依据既有术语表和用户可见性逐项记录。
