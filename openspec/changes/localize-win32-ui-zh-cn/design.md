## Context

Win32 前端的英文静态文案主要位于 `src/drivers/win/res.rc`。当前资源约包含 55 个对话框、12 组菜单和 1800 余行带引号文本；此外，约 42 个 C/C++ 文件直接创建消息框、窗口标题、菜单项和状态文本。Visual Studio 工程的 `CharacterSet` 为 `NotSet`，现有代码大量使用未显式区分 A/W 的 Win32 API，因此直接把整个前端切换到 `UNICODE` 会同时影响文件路径、插件和旧式工具代码，回归范围过大。

该变更服务于简体中文 Windows 用户和使用 TAS/调试工具的进阶用户。英文资源仍是上游维护的基准，简体中文资源必须能独立审查、发现遗漏并在任何不完整状态下回退到英文。

## Goals / Non-Goals

**Goals:**

- 覆盖 Win32 主界面、配置窗口、调试工具、TAS Editor 及运行时提示中的用户可见文案。
- 提供 `Auto`、`English`、`简体中文` 三种选择，稳定持久化并在启动阶段确定资源语言。
- 通过统一术语表得到面向大众、同时不误导 TAS 用户的译文。
- 中文静态和动态文本使用 Unicode Win32 路径显示，不依赖当前系统 ANSI 代码页。
- 以自动检查保证语言资源、格式占位符、快捷键提示和资源 ID 不漂移。

**Non-Goals:**

- 不汉化模拟游戏内容、ROM 元数据、Lua 脚本输出、用户输入、文件路径或第三方库自带界面。
- 不本地化 Qt/SDL 前端，也不在本次变更中增加繁体中文或其他语言的实际翻译。
- 不把整个 Win32 前端迁移到 `UNICODE`，不改模拟核心、配置格式之外的持久数据或 FM2/FM3 等文件格式。
- 不重写窗口布局或现代化 Win32 UI；只做中文显示所需的最小尺寸调整。

## Decisions

### 1. 使用同一可执行文件内的原生多语言资源

保留现有英文资源，并把可翻译的 `DIALOG`、`MENU` 和 `STRINGTABLE` 按语言拆分为英文与 `LANG_CHINESE / SUBLANG_CHINESE_SIMPLIFIED` 资源。中文资源文件使用明确的 UTF-8 resource compiler code page，并由现有 Visual Studio/CMake Win32 构建一并编译；图标、位图、加速键表和版本信息等非语言资源只保留一份。

启动时在创建首个菜单或对话框前设置线程 UI 语言。原生资源与 Win32 的菜单/对话框模型一致，不需要新增运行时解析器或部署外部语言包。相比覆盖原 `res.rc`，该方案保留了英文；相比 gettext/JSON，减少了依赖和资源 ID 到控件的运行时映射；相比资源 DLL，不会引入漏发 DLL 或版本不匹配问题。

### 2. 语言解析使用稳定的三态配置

新增字符串配置值表示 `auto`、`en-US`、`zh-CN`。配置缺失时按 `auto` 处理：Windows 显示语言为简体中文（含简体中文区域变体）时选择 `zh-CN`，其他语言选择 `en-US`；无效值也按 `auto` 安全处理。用户可从 Win32 菜单显式选择语言，选择结果写入现有配置，并在下次启动时统一应用，避免运行中只刷新部分窗口形成混合语言界面。

英文资源是最终回退。某个所选语言资源不存在、资源加载失败或动态字符串 ID 未翻译时，加载器必须再次请求 `en-US`；英文也缺失时才返回带资源 ID 的可诊断占位文本。相比即时切换，重启生效牺牲少量便利，但显著降低长期打开的工具窗口、动态菜单和线程使用不同语言的风险。

### 3. 动态文案集中到字符串表并只在 UI 边界使用宽字符

给消息框标题/正文、窗口标题、状态提示、动态菜单前缀和文件对话框标题/筛选器分配稳定的字符串资源 ID。新增一个 Win32 私有的轻量辅助层，负责按当前语言加载 `std::wstring`、按宽字符格式化并调用显式的 `...W` API。迁移只覆盖本地化文案及其直接 UI 调用边界；现有内部 `char` 数据、文件路径和模拟器核心接口保持不变，必要时仅用已有或集中封装的 UTF-8/UTF-16 转换连接用户数据。

格式化字符串在所有语言中必须保留相同的参数数量、顺序和类型。文件路径、ROM 名称、数值、寄存器名和用户输入作为数据插入译文，不得被翻译或损坏。

### 4. 以语境而非逐字替换维护术语

在 Win32 locale 目录维护可评审的简体中文术语表，并把文案清单中的每一项标为“翻译”“保留”或“中英并列”。采用以下默认规则：

| 类别 | 处理 | 示例 |
|---|---|---|
| 产品名、格式名和行业通行缩写 | 保留原文 | FCEUX、NES、TAS、Lua、ROM、RAM、CPU、PPU、APU、FDS、NTSC、PAL、FPS、FM2/FM3 |
| 已有稳定中文含义的模拟器操作 | 使用简明中文 | Frame → 帧；Save State → 即时存档；Load State → 读取即时存档；Movie → 输入录像；Cheat → 金手指 |
| 容易与日常含义混淆的 TAS 概念 | 首次或空间允许时中英并列，紧凑位置使用统一短译 | Greenzone → 绿区（Greenzone）；Lag Frame → 延迟帧（Lag Frame）；Branch → 分支 |
| 按键、寄存器、标志位和用户数据 | 保持原值 | A/B、Start、Select、PC、IRQ、文件名、十六进制地址 |

同一概念在菜单、对话框和提示中使用同一核心译名。空间不足时只能使用术语表登记的短译，不能临时换词。助记键 `&` 按每个菜单/对话框重新分配，显示的快捷键组合与命令绑定保持原样。

### 5. 资源清单和自动校验作为完成标准

新增一个无第三方依赖的校验脚本，从英文/中文资源及动态字符串表生成 ID 清单并检查：中文覆盖或显式保留状态、资源类型和 ID 对齐、`printf`/格式占位符一致、菜单快捷键后缀一致，以及同一菜单层级明显重复的 `&` 助记键。脚本接入可用的 Win32 构建验证路径；构建仍以 resource compiler 成功为最低门槛。

人工冒烟测试按窗口清单执行，至少覆盖主菜单、常用配置、文件对话框、消息框、调试器、内存工具、Movie 工具和 TAS Editor，并在 100% 与高 DPI 下检查截断、乱码、命令映射和中英切换后的重启行为。

## Risks / Trade-offs

- [英文资源继续演进时中文资源发生漂移] → 用 ID/类型/覆盖清单校验阻止遗漏，并要求新增用户文案同时登记。
- [散落的动态字符串难以一次发现] → 使用 API 调用扫描建立基线清单，分模块迁移，保留每项“翻译/保留/非用户文案”的审计结论。
- [旧的 ANSI 调用导致中文乱码] → 翻译文本统一从宽字符串加载并进入显式 `W` API；不把中文窄字符串传给现有 ANSI UI API。
- [中文长度造成控件截断或高 DPI 布局问题] → 优先短译，按对话框局部扩展控件/窗口，并对关键窗口做 100% 与高 DPI 冒烟检查。
- [专业用户对术语偏好不一致] → 以通行缩写保留和中英并列为保守默认，所有例外集中记录在术语表中，避免代码内自行发挥。
- [语言仅在重启后生效不够即时] → 菜单明确提示下次启动生效；这是避免现有窗口混合语言和复杂重建逻辑的有意取舍。

## Migration Plan

1. 建立英文 UI 清单、术语表、字符串 ID 区间和校验脚本，先让当前英文资源通过基线检查。
2. 加入语言配置解析、启动期资源选择、英文回退和宽字符动态字符串辅助层，并验证英文模式行为不变。
3. 按主窗口/常用配置、调试工具、Movie/TAS 工具的顺序增加中文资源与动态译文，每批运行资源检查和 Win32 构建。
4. 完成两种语言及自动选择的冒烟测试，确认所有窗口清单均有审计结果后再标记完成。

回滚时可移除中文资源和语言菜单，并让辅助层固定选择英文；由于英文资源、命令 ID 和持久数据格式未改变，不需要迁移用户数据。遗留的未知语言配置值会被旧版本忽略，或被新版本按 `auto` 处理。

## Open Questions

当前没有阻塞实现的问题。少数缺乏统一社区译法的工具专名在实现阶段按“保留或中英并列”的规则加入术语表评审，不以未确认的纯中文译名替代。
